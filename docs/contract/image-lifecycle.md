# 图片资源与长任务契约

本文承接 [MODEL.md](../MODEL.md)、[模型持久化契约](./model-representation.md)和[编辑保存契约](./editor-save.md)，定义静态格式、原图保留、3200 万像素／最长边 16384 保护及资源生命周期。内存预算和平台行为需按验收规格实测。

## 1. 输入、原图与显示坐标

- 首期支持静态 JPEG、PNG、WebP、BMP；暂不支持动图、TIFF、PDF、HEIC、AVIF、SVG 等其他格式。必须根据实际内容识别格式并完整解码验证，不能仅凭扩展名接受输入，也不能把动画静默当首帧导入。
- 宽、高均为正整数，最长边不超过 16384 像素，总像素不超过 32,000,000。超限明确说明原因及外部缩图办法；不能为了转成 WebP 就绕过解码前的保护。200 页、每页 100 单元和 50 MiB 不变为直接拒绝导入的产品硬上限。
- 超过 50 MiB 使用 WebP 压缩显示资源，编码与解码同受内存预算；不同时引入 AVIF 编码流水线。小图也可以生成同规格的 WebP 预览和图块，50 MiB 是明确启用压缩的阈值，不是压缩后体积或解码内存的保证。压缩结果只作可重建显示副本，不替换受管原图，也不改变含图导出的原始字节。
- WebP 显示资源按缩略图、预览或视口图块尺寸生成，不要求把整张原图转码后交给 WebView；原始分辨率图块采用无损 WebP，避免细字因额外有损压缩失真。不承诺 WebP 对每种内容都更小，也不承诺压缩后一定低于 50 MiB。
- 原始图片按字节复制并保留，导出使用这些字节；预览、缩略图及原始分辨率显示图块都是可重建资源，不能代替原图。
- 在所选解码器支持并验证的 EXIF 方向信息上统一显示方向；页面宽高、预览和 unit 归一化坐标均以方向校正后的图像为基准。原图仍保留原始字节与元数据，不将显示旋转写回原文件。
- 输入中的标记坐标不因文件名或扩展名猜测而旋转、镜像或重排；交换协议的旧文件坐标映射必须与这里的显示坐标一致。
- 首期显示以常规屏幕翻校为目标，不承诺专业色彩校样、HDR 或保留高位深的显示流水线；原始位深与元数据仍通过原图字节保留在含图导出中。
- 本地路径由 Rust 处理。原始文件名只作为显示和自然排序信息，不参与生成受管路径；无法按既定 Unicode 文件名规则处理的名称明确提示重命名，不用有损替换暗中改变页序。

## 2. 存放与引用

| 范围 | 约定 |
| --- | --- |
| 原图 | 应用数据目录下 `library/<comic-id>/<page-id>/<image-id>.<ext>`，三个身份均由应用生成 |
| 临时准备 | 同一数据卷的 `staging/<task-id>/`，只放本次任务拥有的文件，不作为可见页面引用 |
| 缩略图／预览／图块 | `cache/` 下按不可变图片引用、生成器版本、方向及尺寸定位，可按预算淘汰 |
| `image_reference` | 受控的相对资源引用，固定对应所属 comic/page 和图片版本；不是用户可填写的任意路径 |
| `image_format` | 枚举 `jpeg`、`png`、`webp`、`bmp`，规范扩展名分别为 `.jpg`、`.png`、`.webp`、`.bmp`；依据原图内容确定，原文件名另存 |

- 每次换图产生新的 image-id 和文件，先前原图不可原位覆盖。相同图片导入不同页面也分别拥有文件，首期不引入共享去重或独立图片实体。
- 引用解析校验固定路径结构、对象归属及受管根目录，拒绝绝对路径、路径穿越、符号链接／重解析点逃逸。清理只处理能够证明由本应用拥有的文件，不递归删除未经验证的用户路径。
- 前端通过受限原生资源通道获得当前合法引用的图片；不得任意读取应用数据目录，不通过 IPC 返回整图 Base64 或像素数组。具体 scheme/capability 配置遵循 [IMPLEMENTATION.md](../IMPLEMENTATION.md#3-用例和-ipc) 和 [REQUIREMENTS.md](../REQUIREMENTS.md#72-权限凭据与日志)。

## 3. 解码、缓存与内存目标

以下数字是 8 GB＋SSD 档位的设计预算和验收目标，尚无完整性能实测结果。

| 项目 | 首期预算 |
| --- | --- |
| 完整原图解码并发 | 全应用最多 1 个；当前视口需求优先于后台生成 |
| 原图解码工作空间 | 单任务预估／可控分配预算 768 MiB；包含输入缓冲、原始位深输出、转换与临时空间，不把 RGBA8 大小当成全部内存 |
| 常驻原始分辨率像素 | 最多当前一张，转为 RGBA8 后不超过 128 MiB；切页释放或淘汰旧图，不缓存全 comic |
| 预览 | 长边最多 2048 像素，保持比例；只预取相邻各一页，前端已解码预览总预算 64 MiB |
| 缩略图 | 长边最多 256 像素，按可见区域加载；已解码缩略图总预算 32 MiB |
| 原始分辨率图块 | 按视口请求，单块最多 1024×1024；前端图块缓存总预算 64 MiB，不申请整张超大画布或纹理 |
| 磁盘可重建缓存 | 目标上限 1 GiB，按最近使用淘汰；当前生成中的临时文件另计，完成后立即纳入预算 |
| 应用总体内存 | 常规稳定使用目标 ≤1 GiB，单图解码／导入峰值目标 ≤1.5 GiB；含 Rust 与本应用 WebView 相关进程，GPU 用量另行记录 |

- 32,000,000 像素的 RGBA8 仅输出就约 122 MiB；高位深输入、中间缓冲、压缩数据与 WebView 副本还会增加占用。先做受检查的尺寸／位深／分配估算，再进入解码；满足像素上限不等于任意文件都保证低于工作空间预算。
- 编码图片流式读取／复制，解码器需要缓存的输入也纳入预算。超过可控预算、头部畸形、截断、解码失败或不受支持的表示均明确失败，不把内存分配失败当作正常缩图手段。
- 解码库的分配限制不等同进程级硬内存隔离；必须核实每个启用解码器的限制覆盖，不能只配置一个 Limits 就宣称全部内存受控。实际峰值不达目标时收紧并发／缓存或改进解码，不伪造通过。[官方 Limits](https://docs.rs/image/0.25.10/image/struct.Limits.html)
- EXIF 读取与方向转换的输出预留、复制缓冲均显式计入工作空间；静态 PNG/WebP 额外检查 APNG／动画标识，不把普通 decode 成功当成静态证明。[读取器实现](https://docs.rs/image/0.25.10/src/image/io/image_reader_type.rs.html#146-224)、[方向转换](https://docs.rs/image/0.25.10/image/enum.DynamicImage.html#method.apply_orientation)、[APNG](https://docs.rs/image/0.25.10/image/codecs/png/struct.PngDecoder.html#method.is_apng)、[WebP 动画](https://docs.rs/image/0.25.10/image/codecs/webp/struct.WebPDecoder.html#method.has_animation)
- 初次验证和生成缩略图／预览共用一次完整解码，避免并行重复解码。原始分辨率查看按需生成视口图块；回收原图缓冲后再次查看允许重新解码，不永久占用每页大图内存。
- 预取是有界队列，不从当前页逐渐扩展到全部页面；连续切页时取消尚未开始的过期任务。已运行解码安全完成后可丢弃结果，不能假定取消等待能立即释放解码器。
- 原始分辨率模式不会把低清预览冒充原图细节；图块尚未就绪时显示加载状态。图块和标记使用同一个方向校正后的坐标变换。
- 正常项目启动和缓存页切换依既定响应目标验收；首次大图解码、图块生成、导入和导出单独计时。工程验收明确各平台进程统计口径、共享页重复计数与 GPU 用量，不仅统计 JavaScript heap。

## 4. 准备、提交与清理

| 操作 | 顺序与失败语义 |
| --- | --- |
| 新建／导入页面 | 检查输入与空间 → 复制到 staging → 按副本完整验证并生成预览 → 展示对应关系 → 将全部原图发布到唯一最终路径 → 短事务创建完整内容与引用 |
| 换图 | 先保存草稿，准备并预览新图片 → 发布新文件 → 事务切换引用并按用户选择保留／清空 unit → 提交确认后清理旧原图与缓存 |
| 删除 page/comic | 先保存或按已确认流程处理草稿 → 事务删除内容并修复顺序／工作位置 → 提交确认后清理不再引用的自有文件 |
| 含图片导出 | 保存并取得一致内容快照 → 固定快照涉及的不可变原图引用 → 流式写临时包 → 完成后发布成品并释放引用保护 |

- 用户确认后使用已预览的受管副本，不重新读取可能已改变的源目录。复制、校验、解码、生成资源均不占用长时间数据库写事务。
- 新文件发布与 staging 位于同一数据卷；使用不覆盖已有原图的发布操作，处理冲突和必要的文件同步。数据库与文件系统不存在共同事务，不宣称一次 rename 能让两者原子提交。
- 提交前失败或取消：删除本任务准备的临时和已发布未引用文件，原项目内容保持不变。提交结果不明：先确认引用和写入结果，不立即删除可能已经使用的新文件。
- 提交成功：页面／项目内容已经生效，清理失败不得报告为数据库回滚。清理任务留待重试，并明确区分“内容已完成”与“空间尚未清理”。
- 删除与换图清理必须检查当前数据库引用及活跃导出／读取保护；旧任务不能删除新引用。原始输入目录中的文件从不属于清理范围。
- 长任务使用逐文件进度和已处理字节反馈；文件总数已知时展示总数，解码不可测部分显示阶段状态，不伪造百分比。磁盘剩余空间预估只作前置检查，后续每步仍处理空间不足。
- 首期前台资源任务同时最多一个；文字编辑可在已取得导出快照后继续，但会改动当前任务所涉图片引用的结构操作须协调等待。读出内容快照后释放数据库事务，不在整个 ZIP 写入期间持有读／写事务。

## 5. 取消、退出与启动恢复

- 准备阶段允许取消，停止排入新文件；等待正在执行的不可中断小阶段结束，再清理本任务资源。取消 UI 明确显示正在停止，不宣称点击后文件立即全部消失。
- 进入数据库提交阶段后不承诺撤销，界面改为等待完成；结果不明先确认。提交已经成功就报告完成，不能因较晚到达的取消请求伪报为已取消。
- 正常退出时，未提交资源任务先取消并收尾；提交中的任务等待结果确认，再执行保存契约的退出协调。导出未完成的临时文件不作为成品交付。
- 启动时先取得数据目录排他锁、完成数据库迁移，确认引用可读后再处理残留；迁移或数据库读取失败时禁止把“读不到引用”解释为全部文件可删除。
- 通过 staging 任务目录及受管原图命名识别候选残留。无活跃任务的启动恢复中，只清理确认无引用、无保护且格式／归属均合法的应用自有文件；不按文件年龄猜测原图是否可删，不清扫未知文件。
- 应用崩溃或断电仍可能造成资源异常；不能以正常取消的测试替代这一边界。清理失败保留可重试状态，不通过删库或删除现有引用“修复一致性”。

## 6. 丢图与缓存损坏

- 缩略图／预览／图块损坏时删除对应缓存并从原图重建，不改变 page/unit 身份或内容时间。
- 原图丢失或不可读时保留资料和单元，明确标出异常页。可用缓存可以辅助显示，但必须说明原图异常，不能据此宣称原图已恢复或含图导出完整。
- 无任何可用图像时禁止依赖图像定位的新增／拖动标记，仍允许查看和编辑已有文本，并允许译文导出。含图导出按照既定规则整次失败。
- 修复入口采用既定“为该页重新选择图片”流程，展示预览并明确保留／清空单元；不根据文件名自动替换其他页面，不扫描原目录猜测匹配。

## 7. 验收场景

- 格式：内容与后缀不一致、动画、损坏／截断文件、EXIF 方向、透明度、高位深、像素和工作空间边界。
- 资源：200 页级项目有界预取、长图原始分辨率查看、快速切页取消、连续生成时的稳定与峰值内存、缓存淘汰后重建。
- 失败：复制／发布／事务／提交确认／旧文件清理分别失败，空间不足，提交前取消和提交期间取消，强制终止后启动恢复。
- 安全与完整性：路径穿越、符号链接／重解析点、未知文件不误删、迁移失败不清扫、导出中的引用不被清理、原始输入文件不被改动。
- [文件交换协议](../IMPLEMENTATION.md#2-文件交换)承接规范格式扩展名、原图字节、方向坐标、一致快照和临时包发布；ZIP 条目及压缩包解压防护见该协议。
- [用例与 IPC 契约](../IMPLEMENTATION.md#3-用例和-ipc)承接图片句柄、按需图块、阶段进度、取消与结果确认；[验收与交付要求](../IMPLEMENTATION.md#6-验收与交付)固定实际解码器、平台样例和量测方式。
